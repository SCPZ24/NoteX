## 1. 产品目标与范围原则

建设一个可以实际使用的公开短内容社区：用户注册登录，查找并关注作者，发布或删除短帖，在关注首页阅读内容，并通过关键词搜索帖子。

首版的工程工作正好围绕以下五个 Slot 展开：

| Slot | 工程主题 | 对应产品能力 |
|---|---|---|
| S1 | Fanout 与推拉结合 | 不同粉丝规模的作者，其内容都能进入正确用户的关注信息流 |
| S2 | 关注关系建模与查询优化 | 关注、取关、关系判断、关注列表与粉丝列表 |
| S3 | 近实时搜索索引与同步 | 新帖最终可搜、删帖不再展示、搜索故障后可追平 |
| S4 | 可靠发布与异步事件处理 | 已确认的业务变化可持久化，其必要异步工作可恢复、可重试 |
| S5 | 热点缓存、受控回源与重建 | 缓存缺失或故障时保护主存储，并恢复正确读取能力 |

**范围原则：完成这五个主题及其必需的用户闭环，不继承参照项目的全部功能。**


## 2. 用户、主流程与最小页面

### 2.1 用户角色

- **已登录用户**：发布和删除自己的帖子，关注其他用户，阅读公开内容和搜索帖子。
- **测试／维护人员**：通过内部工具查看失败任务、触发重放和重建、执行验收。首版不建设独立运营后台或复杂角色权限系统。

“公开”表示所有已登录用户均可访问，不因是否关注作者而改变帖子本身的访问权限。首版不提供游客使用流程。

### 2.2 两条必须闭合的主流程

**关注阅读流程：** 注册／登录 → 查找作者 → 关注 → 作者发帖 → 读取关注首页 → 查看帖子详情 → 取关。

**搜索与删除流程：** 发布短帖 → 在个人主页确认发布结果 → 关键词搜索到帖子 → 作者删除 → 新的详情、列表和搜索请求不再展示该帖。

异步处理期间允许内容尚未进入关注首页或搜索结果，但不能将已经成功提交的帖子误报为发布失败。

### 2.3 最小页面

| 页面 | 必需内容 |
|---|---|
| 注册／登录 | 用户名、密码、错误提示、退出入口 |
| 关注首页 | 发帖入口、关注 Feed、刷新、加载更多、空态与服务异常提示 |
| 用户主页 | 用户名、作者帖子列表、关注／取关、关注列表和粉丝列表入口 |
| 帖子详情 | 作者、正文、发布时间；作者自己的删除入口 |
| 查找入口 | 按准确用户名查找用户；按关键词搜索公开帖子 |

页面可合并、复用现成前端。视觉重做、复杂交互和客户端适配不是验收目标。

## 3. 全局业务约定

以下约定对正常路径、降级路径、缓存重建和所有对照实验均有效。

| 编号 | 约定 |
|---|---|
| G-01 | 帖子首版只支持纯文本、公开可见；正文发布后不可编辑，只能删除。 |
| G-02 | 正文去除首尾空白后必须非空，长度上限默认 500 个 Unicode 码点，不按 UTF-8 字节数计数。 |
| G-03 | 关注是单向关系；不支持关注自己，不支持对不存在的用户建立关系。 |
| G-04 | 关注首页展示“当前关注作者＋自己”的未删除帖子，按不可变的发布时间倒序，同时间按帖子 ID 倒序。 |
| G-05 | 个人主页采用同样的帖子排序；评论顶帖、置顶、热度排序均不进入首版。 |
| G-06 | Feed 和个人帖子列表默认每页 20 条，上限 100 条；使用确定性游标继续读取，不要求任意页码跳转。 |
| G-07 | 发布成功表示帖子及其必需的异步工作已经可靠记录，不表示所有粉丝已看到，也不表示搜索已经可见。 |
| G-08 | 删除或取关成功之后开始的新请求，必须按最新有效状态过滤内容；与修改并发、已经开始执行的读取不承诺追溯撤回。 |
| G-09 | Redis 和搜索索引属于可恢复的派生数据；它们的缺失不等于帖子或关系从主存储消失。 |
| G-10 | “空结果”“尚未完成加载／重建”“依赖故障”“超过服务能力”必须可区分；不能将异常伪装成成功的空列表。 |

### 3.1 翻页保证的边界

在数据和关注关系不变、异步处理已追平的条件下，连续翻页应保持顺序确定，无重复、无遗漏。

持续有新帖进入时，新帖通过刷新获取，不通过 OFFSET 位移挤乱已有分页。异步晚到且排序位置已经翻过的内容，允许通过刷新出现。首版不承诺跨多次请求的全量快照，也不承诺关系变化前后的游标仍代表同一个快照。

删除／取关过滤掉候选项后，不能仅因该批候选不足一页就错误宣告历史结束。实现应在有界工作量内继续获取有效候选，或明确返回可继续读取的状态。

### 3.2 历史内容范围

关注一个作者后，允许浏览该作者已有的公开内容；初始历史补入／预热默认只处理最近 20 条，以限制后台工作量。

该数值是预热范围，不是永久可见性上限。用户继续向后翻页时，近期索引之外的内容仍应有受控读取途径。缓存容量不能悄悄改变产品的数据范围。

## 4. 功能需求

### 4.1 账号与基础访问（MVP，不单独占 Slot）

| 编号 | 需求 | 验收结果 |
|---|---|---|
| A-01 | 用户名＋密码注册；用户名唯一，规则前后端一致 | 可注册新账号，重名或无效输入返回明确错误 |
| A-02 | 登录、保持当前登录态、退出 | 登录后能执行受保护操作，退出后当前使用流程要求重新登录 |
| A-03 | 写操作必须依据服务端确认的身份 | 不能伪造作者身份发帖或删除他人帖子 |
| A-04 | 保留必要的密码保护、输入校验和文本安全展示 | 不明文保存密码，不向客户端暴露敏感凭据，不将帖子文本直接当作可执行页面内容 |

复用底座的基础账号能力即可。不增加手机／邮箱验证、第三方登录、找回密码、个人资料编辑、复杂风控和多端会话管理。

### 4.2 发布、查看与删除帖子（支撑 S1／S3／S4）

| 编号 | 需求 | 验收结果 |
|---|---|---|
| P-01 | 发布符合 G-02 的文本帖子 | 返回稳定帖子 ID；提交后开始的个人主页／详情读取能看到帖子 |
| P-02 | 同一发布意图支持重试 | 同一用户、同一请求标识、同一内容不会重复建帖；同标识但内容不同应拒绝 |
| P-03 | 发布重试识别窗口默认不少于 24 小时，并跨应用重启有效 | 响应丢失后重试仍返回原帖身份；原帖已经删除时，不因重放而创建新帖 |
| P-04 | 查看个人帖子与帖子详情 | 正确展示作者、正文和发布时间；列表满足 G-05、G-06 |
| P-05 | 作者删除自己的帖子；重复删除不会重新产生业务效果 | 删除状态可靠保存，已删除内容不能被旧事件重新公开 |
| P-06 | 区分提交失败与结果暂不确定 | 请求超时不自动等同于未提交；客户端可使用原请求标识安全重试 |

用户拿到成功结果后，即使应用进程强制退出，重启后也应能查回其已提交内容。测试边界见第 6 节。

### 4.3 关注关系（S2）

| 编号 | 需求 | 验收结果 |
|---|---|---|
| R-01 | 按准确用户名找到作者并进入主页 | 用户可以在没有推荐算法或发现页的情况下建立第一条关注关系 |
| R-02 | 将关系设为“已关注”或“未关注”，而不是每次调用都翻转状态 | 重复关注不新增重复关系，重复取关不报成不可恢复错误 |
| R-03 | 判断当前用户是否关注目标作者 | 界面状态与主存储一致 |
| R-04 | 分页查看某人的关注列表与粉丝列表 | 两个方向都能查询；固定数据下连续翻页无重复、无遗漏 |
| R-05 | 关系列表按建立时间倒序，同时间按稳定关系标识排序 | 新关系插入不造成基于页码位移的重复展示；不要求按名字任意排序 |
| R-06 | 并发关注／取关后收敛到一个有效状态 | 最终状态按服务端实际完成的变更次序解释，不承诺按客户端点击时间自动判定最后意图 |

关注成功后应触发必要的历史补入工作；取关成功后开始的新 Feed 请求不再展示该作者内容。重新关注后，新的有效关系不能被迟到的旧清理工作破坏。

取关仅影响个人关注 Feed，不影响公开帖子通过作者主页、详情或搜索被访问。

### 4.4 关注 Feed（S1，部分依赖 S4／S5）

| 编号 | 需求 | 验收结果 |
|---|---|---|
| F-01 | 聚合当前关注作者与自己的有效帖子 | 满足 G-04，多个来源合并后同一帖子只出现一次 |
| F-02 | 普通作者与大粉丝量作者均可正常发布与被阅读 | 两类路径的最终用户可见结果遵循同一业务规则 |
| F-03 | 支持推模式与拉模式的混合策略 | 工程验收能够对照 SQL 拉取、纯推、混合策略的读写成本 |
| F-04 | 发帖后异步进入粉丝 Feed | 在冻结的目标负载下达到规定的发布到可见时效，不以 API 返回速度冒充分发完成速度 |
| F-05 | 新关注支持历史内容补入 | 最近 20 条作为默认预热范围；在规定时间内可读，旧帖范围遵循 3.2 |
| F-06 | 取关、删帖与迟到事件交错时仍按当前状态展示 | 不展示已取关作者的 Feed 内容，不展示已删除帖子 |
| F-07 | 读取近期索引之外的页面 | 能继续读取合法历史，不把缓存裁剪误认为没有更多内容 |
| F-08 | 大任务与普通任务共存 | 后台处理工作量和资源占用有上限，普通任务能够持续推进 |

首版允许在启动或实验开始前，根据粉丝规模快照和配置确定作者策略；同一运行／验收轮内保持固定。动态跨阈值迁移、自动调参和线上灰度不属于本版。

### 4.5 内容搜索（S3）

| 编号 | 需求 | 验收结果 |
|---|---|---|
| S-01 | 对公开帖正文做关键词搜索 | 固定中英文样本能够按预期匹配；复用搜索引擎基础分词与相关性能力 |
| S-02 | 展示匹配帖子的作者、正文或摘要、发布时间和详情入口 | 不需要推荐理由、语义解释或复杂筛选 |
| S-03 | 支持基本分页 | 首版仅要求前 100 条匹配结果内的分页；不要求深搜索分页与跨页快照 |
| S-04 | 新帖在规定时间内可搜索 | 验收以搜索接口实际返回该帖为准，不以索引写入请求已受理为准 |
| S-05 | 删除成功后开始的新搜索请求不展示该帖 | 搜索索引允许异步清理，但用户可见结果必须过滤失效内容；无法核实关键状态时不能返回未经确认的正文 |
| S-06 | 搜索故障不阻塞已允许接受的发帖与 Feed 业务 | 搜索页面明确报暂不可用；不能悄悄改成无界数据库全文扫描 |
| S-07 | 搜索恢复后处理停机期间的新增、删除 | 有效数据追平；重复／旧事件不能让已删除内容复活 |
| S-08 | 搜索索引丢失后可重建 | 首版允许暂停内容写入完成重建；不承诺不停写重建 |

不做向量检索、RAG、搜索推荐、热搜、自动补全或自研相关性排序。

### 4.6 故障表现与恢复（S4／S5）

| 编号 | 场景 | 产品要求 |
|---|---|---|
| X-01 | 已提交后应用或后台处理进程退出 | 重启后找回待处理工作；不能只恢复进程而遗漏业务结果 |
| X-02 | 消息系统暂时不可用 | 主存储及持久待办容量允许时可继续接受写入；超过既定容量时受控拒绝，不能丢弃已承诺成功的工作 |
| X-03 | 同一事件重复、迟到或部分执行后重试 | 最终结果不重复、不倒退，且遵守删除与关系规则 |
| X-04 | 永久失败或不合法任务 | 留下可查询失败记录及可操作的重放／处置入口；不以进入死信状态冒充完成 |
| X-05 | 单个热点缓存缺失 | 合并不必要的重复回源，不让所有相同请求各自执行同一昂贵查询 |
| X-06 | 大量不同缓存同时缺失或整个缓存服务不可用 | 限制总回源和重建资源，保留冻结的最低有效读取能力；超限及时明确拒绝 |
| X-07 | 缓存恢复时仍有新的内容和关系变化 | 重建后结果正确，不被旧快照覆盖新增内容，不恢复不再有效的内容 |
| X-08 | 权威数据暂不可用 | 不返回未经提交的写入成功；不能在无法核实删除／关系状态时伪造正确结果 |

失败任务查看、重放、重建及相关指标可以通过命令行或仅维护者可访问的工具提供。不建设新用户侧功能或通用工作流平台。

## 5. 一致性与可靠处理范围

### 5.1 哪些操作必须可靠记录？

所有向用户承诺成功的业务写入都必须有明确的持久化结果。只有存在不可静默遗漏的跨系统副作用时，才要求额外的可恢复异步工作。

| 业务变更 | 必须完成的后续工作 |
|---|---|
| 发布帖子 | Feed 分发／可读取性更新；搜索索引新增 |
| 删除帖子 | 搜索删除同步；必要的派生状态清理，且用户侧立即遵守删除过滤规则 |
| 关注 | 持久关系变更；约定的历史补入与可读取性更新 |
| 取关 | 持久关系变更；必要的派生状态维护，读取侧立即遵守关系过滤规则 |
| 注册、登录等纯账号操作 | 满足自身业务承诺；没有必要的外部副作用时，不要求附加消息任务 |
| 非关键缓存预热或统计 | 可按明确约定尽力而为，但不能承载本应可靠完成的必需功能 |

“操作可重复执行”与“该操作可以静默丢失”是两件事。删除和取关即使具有幂等语义，其必要的后续同步也不能被忽略。

### 5.2 最终一致性的边界

新增帖进入 Feed 和搜索允许异步延迟；允许的时间范围由验收配置冻结。超过范围的工作必须能够被识别为积压或失败。

对于删除和取关，派生存储的物理清理可以异步进行，但新读取的展示结果必须符合 G-08。客户端已经显示的旧页面不要求被主动推送擦除。

有限抽样可以用于发现异常；不能将抽样未发现问题表述为全量绝对无遗漏。

## 6. 质量目标与验收口径

### 6.1 首版直接固定的要求

- 在指定正确性测试集和故障轮次内，违规展示、重复业务实体和静默遗漏均为 0。
- 纯推、纯拉和混合 Feed 在静止、追平后的参考结果一致。
- 缓存故障时，同时验证资源受控和最低有效服务能力；全部拒绝请求不算降级成功。
- 搜索重建可暂停写入；Timeline 缓存重建必须覆盖恢复期间继续发帖的场景。
- 账号、Feed、搜索、维护入口分别有正常、空结果和异常表现。

### 6.2 正式性能验收前必须冻结的参数

硬件与服务资源尚未确定，因此本 PRD 不虚构统一的毫秒／QPS 指标。以下内容在基线摸底后、优化对照前记录到验收配置；空缺时不得宣称通过完整性能验收。

| 参数组 | 必须明确的内容 |
|---|---|
| 数据与负载 | 用户数、关系数、帖子数、粉丝分布、读写比例、请求到达速率、返回条数 |
| 正常服务 | Feed／关系查询／搜索的成功率目标及 P95／P99 延迟预算 |
| 异步时效 | 普通作者 Feed 可见时效、搜索可见时效、关注历史补入时效 |
| 故障服务 | 回源任务准入与并发上限、重建并发上限、最低成功读取速率、超限响应期限 |
| 恢复目标 | 依赖恢复后的追平期限、指定规模缓存重建期限、失败任务处置方式 |
| 实验条件 | 版本、实例数、CPU／内存额度、持久化设置、连接池与关键批量参数、预热状态 |

性能提升是实验结果，不是预先写入的事实。未取得显著提升时应如实交付结论，不制造不公平基线。

### 6.3 故障保证的范围

首版验证单环境内的应用进程退出、容器强制退出、依赖短时停机、重复消息，以及可重建派生数据丢失。

MySQL 与消息系统的持久化数据在重启实验中保留。首版不承诺磁盘损毁、机房故障、跨地域容灾或生产集群高可用。

## 7. 不进入首版的功能

| 类别 | 明确排除 |
|---|---|
| 互动扩展 | 点赞／取消点赞、点赞计数、评论、收藏、转发、通知中心；第六个 Slot 不默认加入 |
| 社区扩展 | 热榜、趋势检测、推荐算法、多级可见性、好友双向关系、拉黑、付费内容、运营审核后台 |
| 媒体与通信 | 图片／视频／附件上传、私信、群聊、WebSocket 实时推送、音视频 |
| Agent 能力 | 聊天助手、RAG、多 Agent、向量检索 |
| 大型基础设施 | 图数据库、分库分表、动态策略迁移、搜索不停写重建、多地域容灾、通用任务编排平台 |

上游已有这些功能，不代表需要在首版对用户开放或继续维护其业务路径。保留代码与纳入验收是两个不同决定。

## 8. 需求到验收的对应关系

具体实验与产物见《首版实现方针》。以下对应关系用于防止功能做完后找不到证据，或验收时临时扩张范围。

| 主题 | 主要需求编号 | 必需验收类型 |
|---|---|---|
| MVP | A-01～A-04、P-01～P-06、R-01 | 正常闭环、身份与越权、重试及错误提示 |
| S1 Feed | F-01～F-08、G-04～G-06、3.1～3.2 | 三种策略对照、混合负载、结果核对 |
| S2 关系查询 | R-02～R-06 | 双向查询、游标深分页、并发关系修改 |
| S3 搜索 | S-01～S-08 | 实际可见性、删除／重放、停机追平、停写重建 |
| S4 可靠事件 | P-02～P-06、X-01～X-04、第 5 节 | 指定执行窗口故障注入、任务追平、失败处置 |
| S5 缓存韧性 | X-05～X-08、F-06～F-07 | 热点击穿、大面积失效、受控降级、并发重建 |

## 9. 首版完成定义

首版完成需要同时满足：

1. 两条用户主流程可通过实际界面使用，必需功能与错误状态均接入真实后端。
2. 五个 Slot 的正确性、故障恢复及适用的性能对照有可重复运行的验收记录。
3. 所有对外声明的性能／规模都有对应环境、数据、版本和原始结果，不引用上游成绩冒充本项目成绩。
4. 失败任务、积压与恢复过程能够检查和处置，不依赖临时手工改数据库才能完成已承诺业务。
5. 未纳入首版的功能没有成为主流程的强制依赖；已知限制在交付说明中明确记录。

**五条分别做深即可。不通过新增旁路业务填满简历，也不将编写代码完成视为验收完成。**
