# Sprint 4：搜索同步和故障恢复

> 主线：S3，并补齐 S4 的搜索副作用验证；建议窗口：2026-11-17。  
> 前置：可靠事件骨架、帖子权威状态和删除规则。Feed 与搜索共享事件来源，但分别完成自己的工作。  
> 共同约定见 [Sprint 1](./1-基础闭环和权威数据查询.md)。

## 1. 核心问题

**事件已经送达、搜索引擎已经受理、用户真的搜到了，这三个时刻为什么不同？删除和故障恢复时，如何保证结果最终正确？**

重点是同步链路、可见性和恢复能力，不是自研搜索引擎或相关性算法。

## 2. 学习目标

| 知识 | 必须能够解释 |
|---|---|
| 权威状态与搜索索引 | 索引可能暂时滞后，但不能据此展示已删除正文 |
| 独立消费路径 | Feed 和搜索都需要事件，不能相互竞争掉必要任务 |
| 搜索异步任务 | 写入受理不等于任务成功，也不等于实际查询可见 |
| 批量处理 | 批量大小和最大等待时间分别影响吞吐与延迟 |
| 重复与迟到事件 | 消费时需要考虑最新状态，旧创建事件不能复活删帖 |
| 重建与追平 | 故障期间积压恢复与整个索引重新生成是不同工作 |

## 3. 实现顺序

1. 接通关键词搜索与页面，固定中英文样本和基本分页；按 PRD 只要求前 100 条匹配范围。
2. 建立独立搜索消费与任务跟踪，区分受理、执行、失败和用户可见。
3. 先完成逐条索引，再增加同时有大小、等待时间上限的小批量方案。
4. 删除成功后的新读取核实权威状态；异步索引清理最终收敛。不能仅依靠页面过滤掩盖长期错误索引。
5. 搜索停机后恢复追平，主业务在接受预算内继续；搜索页返回明确异常。
6. 实现停写索引重建与结果核对；不扩展不停写重建。
7. 注入“搜索已受理、本服务未记录结果”和“部分索引工作后退出”的故障，验证重试恢复。

```mermaid
flowchart LR
    A[业务提交] --> B[可靠事件]
    B --> C[搜索消费者]
    C --> D[引擎受理任务]
    D --> E[索引任务完成]
    E --> F[实际搜索返回]
    F --> G[核实有效状态后展示]
```

发布到搜索首次可见延迟从首次发布请求发出计时，不能只测 D 到 E。

## 4. 验收与证据

- **S3-A：** 固定中英文关键词、预期 ID、正文与作者、无匹配和异常状态。
- **S3-B：** 固定发帖速率，逐条与小批量对照；报告实际可搜索 P95/P99、有效索引吞吐、任务成功与失败以及等待代价。
- **S3-C：** 重复创建、删除后迟到创建；分别检查用户不可见与最终索引正确，二者缺一不可。
- **S3-D：** 搜索停止 60 秒，继续发布和删除；报告发帖／Feed 成功率、积压与指定事件追平时间。
- **S3-E：** 暂停内容写入，清空隔离测试索引并重建；核对有效文档 ID 与字段，不仅比较总数。
- **S4 补验：** 外部系统受理后本服务退出、部分索引工作失败、重复投递与显式重放；执行相应故障轮次并保留业务结果。

可见性观察与发压同时进行，未完成与超时样本单列。报告抽样范围，不能拿一条演示查询代替整个负载的可见性结论。

到本 Sprint，应通过真实页面接通两条 PRD 主流程：关注阅读，以及发布—搜索—删除。缺少的页面接线在这里暴露，不拖到最终演示才发现。

## 5. 技术 insight 与面试产物

形成一份时序图、一份逐条／批量对照，以及一次停机追平记录。能够回答：

1. 为什么 MQ 已经空了，仍可能不能搜索？
2. 为什么不能让 Feed 和搜索消费者直接竞争同一份必须分别处理的工作？
3. 批量索引如何平衡低流量等待与高流量吞吐？
4. 删除过滤解决哪个阶段的问题，为什么还要清理索引？
5. 为什么此处接受停写重建？与不停写方案相比主动放弃了什么？

简历写自己的同步、恢复和测量工作，不把 Meilisearch 本身的检索能力写成个人研发成果。

## 6. 完成门槛与超时处理

完整完成要求正确匹配、可见性对照、删除与迟到事件、停机追平、停写重建及对应真实副作用窗口都有记录。

时间不足时优先正确同步与故障恢复，批量优化保留为未完成实验；不添加相关性调优、自动补全或向量检索。没有实测批量收益就不写“提升索引吞吐”。达到简历收口日期后，根据已验证程度决定是否作为独立简历亮点。

## 7. 参考代码与阅读顺序

**参考程度：Paopao 已有 Meilisearch 适配和同步入口，可以参考接入方式；可靠同步与可见性验收需要自己补齐。** 本 Sprint 不把 WeBook 搜索模块加入必读范围，避免引入另一套搜索实现。

| 顺序 | 代码入口 | 重点阅读与用途 |
|---|---|---|
| 1 | [core/search.go](paopao-ce/internal/core/search.go)、[dao/search/search.go](paopao-ce/internal/dao/search/search.go) | 理解已有搜索接口和适配组织，优先复用当前 Meilisearch 路径 |
| 2 | [dao/search/meili.go](paopao-ce/internal/dao/search/meili.go) 的 `AddDocuments`、`DeleteDocuments`、`Search`、`toDocs` | 阅读文档映射、增删和查询，找出任务结果没有被完整跟踪的位置 |
| 3 | [servants/base/base.go](paopao-ce/internal/servants/base/base.go) 的 `PushPostToSearch`、`pushPostToSearch`、`DeleteSearchPost`；[base/events.go](paopao-ce/internal/servants/base/events.go) | 追踪业务到索引的单帖同步，以及进程内事件挂接方式 |
| 4 | 同一 `base.go` 的 `PushAllPostToSearch`、`pushAllPostToSearch`；[jinzhu/tweets.go](paopao-ce/internal/dao/jinzhu/tweets.go) 的 `ListSyncSearchTweets` | 借鉴全量读取与文档构造；重新设计符合停写重建和全量核对的流程 |
| 5 | [servants/web/loose.go](paopao-ce/internal/servants/web/loose.go) 的 `Timeline`；[dao/search/filter.go](paopao-ce/internal/dao/search/filter.go) | 跟踪用户查询与既有过滤层，改为本 PRD 的公开内容和删除规则 |

**不能直接照搬：** `AddDocuments` 丢弃返回的任务信息后返回成功，`DeleteDocuments` 仅记录任务信息；都不能证明任务执行成功或用户已可搜索。全量同步循环虽按页读数据库，但内层仍逐帖提交，不能称为已经实现小批量索引优化。既有置顶、最近回复排序和多级可见性也不能直接成为 NoteX 的业务语义。

**需要自行实现：** 对接 S4 的独立可靠搜索消费、任务状态与不确定受理结果的恢复、实际查询可见性观察、有大小／等待上限的批量处理、删除后权威过滤和最终清理、停机追平，以及停写重建的 ID／字段核对。上游存在“全量推送入口”不等于本项目重建验收已通过。
