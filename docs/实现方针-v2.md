## 1. 决策摘要

保留 Sprint 2 的外部业务契约、历史实现与回归测试，不要求永久冻结内部表结构或处理器接口。

最终四条工程主线：

| 主线 | 核心问题 | 不单独占条目的基础功能 |
| --- | --- | --- |
| 时间线生成与分发优化 | 把哪些计算放在发布时，哪些放在读取时；如何限制写放大与重任务干扰 | 关注表、索引、游标、基础 Feed |
| 可靠的派生数据维护 | 已提交事实如何可靠传播，重复、迟到、部分执行后如何收敛 | Outbox、CDC、Meilisearch 接入 |
| 热点缓存与一致性恢复 | 如何减少重复回源，拒绝过期回填，正确重建丢失缓存 | 普通缓存、Lua、内容批量读取 |
| 分布式执行与服务治理 | 多实例如何扩容、发现彼此、限制资源、隔离故障和恢复服务 | RPC、注册发现、配置、部署 |

推荐保留 Go、MySQL、Redis、RabbitMQ、Meilisearch；新增 gRPC 与 etcd。Debezium Server 作为 CDC 实验组件，不为接入它额外引入 Kafka。Kafka、TiKV、自研 Raft、自研分布式数据库、动态分库分表不进入本轮。

实施优先级：外部消费者协议与真实 Fanout > 缓存并发恢复 > 多实例治理 > CDC 对照与受控切换。CDC 可并行做小型可行性验证，但不能拖住整条真实业务链路。

## 2. 当前代码核对结果

### 2.1 发布成功路径

`src/internal/post/service.go` 的 Create 在同一事务中执行：

1. INSERT post_requests。
2. SELECT 作者。
3. INSERT posts。
4. UPDATE post_requests，记录 post_id 和首次响应。
5. RecordPost 写入 outbox_events。
6. COMMIT，之后通知后台。

这是四条修改语句和一次作者查询，不含鉴权。SQL 次数、逻辑记录写入、提交次数、物理磁盘 I/O 必须分别统计，不能画等号。

### 2.2 发布器

`outbox/publisher.go` 在成功发送路径中会分别更新 attempts 与 published_on。批量扫描为 32 条，有提交后合并唤醒和 5 秒恢复扫描。SQL 查询结束后才进行网络发布，没有跨 Broker 等待持有数据库事务锁。

### 2.3 消费者

`outbox/consumer.go` 使用 SQLHandler(context.Context, *sql.Tx, Event)。正常消息先保存 consumption_jobs，再查询、锁行、执行 SQL 副作用和更新完成状态。当前 QoS 为 1，单会话逐条处理。

这是 SQL Dummy 效果的恢复基线，不是 Redis/Meilisearch 外部效果的完整事务。注释也明确提醒外部写入需要独立恢复协议。不得把它直接复用为每个粉丝一条 SQL 消费日志。

### 2.4 事件信息

现有 Event 含事件 ID、类型、payload、created_on；关注 payload 只有双方用户 ID。没有直接提供可用于拒绝旧关系清理的业务版本或关系生命周期身份。事件 ID 不能未经证明就当作事务提交顺序或清理水位。

## 3. 仍须保持的业务契约

- 发布成功表示权威帖子与必要异步意图已可靠记录，不等于所有派生视图可见。
- 同一用户、同一发布标识、同内容重试不重复创建；同标识不同内容拒绝；删除后重放不能重新创建帖子。
- 删除或取关成功后开始的新读取，应按最新有效状态过滤。
- Redis 和搜索是派生数据。缓存缺失、未构建、真实空列表、依赖错误必须区分。
- 异步延迟、工作量、失败次数、保留窗口均有明确上限或预算。
- 当前项目为纯后端，不重新加入前端工作。

尤其不能暗中将强过滤语义改成“最多一分钟陈旧”。在未设计等价的权威检查协议之前，读取主库中的小批量有效性信息属于明确保留的成本。

## 5. 写入与可靠性路线选择

| 路线 | 能减少什么 | 仍需付出的代价 | 定位 |
| --- | --- | --- | --- |
| 现有 Outbox 轮询 | 当前基线，无迁移 | 源业务事务、扫描、状态更新、幂等与恢复 | 保留可回退实现 |
| Outbox + CDC | 避免应用扫描；设计正确时正常路径可不逐行回写投递状态 | Outbox INSERT 仍存在；日志与 CDC 存储、运维、重复 | 第一组 CDC 对照 |
| 直接业务表 CDC | 可去掉能从业务行变化恢复的 Outbox INSERT | 行变化到领域事件的映射、schema 耦合、版本、删除、快照与位点 | 测量后选择性采用 |
| 日志优先 | 受理链路可不先提交 MySQL | 主存储语义变化；去重状态、分区处理、读己之写和持久化复制仍有成本 | 本轮不选 |

### 5.1 推荐渐进路线

先做外部处理器，避免下游正常路径无条件回到 MySQL 记账。

再建立可替换的事件来源：Outbox 轮询与 CDC 归一化输出同一事件契约。在影子队列/影子投影中比较，不直接同时修改正式投影。

CDC 首轮捕获 Outbox 的新增事件，保留稳定事件身份。只有当业务表能无歧义表达必要变化，且端到端验证通过后，才切换该类事件到业务表 CDC。不能在切换协议尚未完成时删掉 Outbox 写入。

“SQL 次数减少”不是整体性能收益的充分证据。比较 CPU、内存、磁盘、redo/binlog 增量、事务延迟、事件延迟、恢复成本，以及新增组件的资源。

### 5.2 CDC 必须验收的边界

- 固定并实测 MySQL、Debezium、RabbitMQ 兼容组合；仓库描述的目标版本和本机已测版本不能直接当作 CDC 兼容结论。
- 使用 connector 支持的日志/快照模式，不自己拼一个未经证明的 MAX(id) 水位。
- 可靠保存 offset 与 schema history；进入下一位点以前，相关消息已经按 sink 语义可靠交付。
- 容忍确认丢失造成的重发；检查目标绑定、不可路由、持久化和确认设置。
- 监控日志保留量与 CDC 落后时间。位点对应日志已被清理时，停止伪装正常，执行显式重建流程。
- 新快照不自动删除旧投影中的幽灵记录；需构建新投影代次或进行完整集合对账。
- 行变更不等于领域命令。多表事务需有明确归一化规则，不能每个变动行都盲目触发重复副作用。
- 初版切换允许受控暂停相关写入、排空在途、固定一致边界。保留旧源和数据，回退可选择有界重放；不承诺在线无损任意切换。
- 不把 CDC connector 的单点重启恢复宣传成整个系统高可用。

### 5.3 request_log / post_requests

它承担请求幂等与首次响应重放，CDC 不替代这个功能。

首轮保留。后续可比较独立窄表与业务表内幂等字段两种实现，但必须保留请求识别窗口、删除后的身份、同键异内容拒绝、原结果恢复等契约。内容摘要是否能替代正文、是否仍需存首次响应，应单独论证。不能只用易失 Redis SETNX 替换跨重启幂等承诺。

## 6. 主线一：时间线生成与分发优化

### 6.1 必做

- 保留现有 SQL Feed 为参考实现，不删除合理索引以制造低效基线。
- 作者个人索引与读者首页索引分离；索引保存帖子身份和排序数据，不逐粉丝复制全文。
- 普通作者写时扩散，大作者读时聚合；首轮策略按固定名单或冻结阈值决定。
- 多来源以统一排序键(created_on, post_id)归并；先聚合候选，再批量读取正文与校验有效状态。
- 分发按稳定游标拆成小批，Pipeline 降低往返；单个任务和单个 Lua 操作都要有工作量上限。
- 重任务、普通分发、历史补入与恢复任务分别分配资源预算。
- 同一事件重复后结果不重复；迟到删除/关系清理不可破坏新状态。

### 6.2 任务交接

Fanout Planner 每次展开一个有界粉丝页，将该页子任务与后续游标任务可靠发布并收到确认后，才 ACK 当前消息。崩溃可能造成重复交接，所以任务身份与效果必须可重做；不能承诺调度本身 exactly-once。

游标基于实际关系模型定义，需覆盖并发关注/取关；新增关注由其历史补入路径补齐。不要把可变粉丝集合当成无需证明的静态快照。

不要求每个粉丝先 INSERT 一条 SQL 日志。必要 checkpoint 按根任务或分块记录，不按所有对象无差别记账。

### 6.3 可选第二层

在基础混合策略验收后，再研究活跃读者选择性物化。它必须包含冷用户上线补齐和历史读取能力，不能通过静默少分发换数据。

### 6.4 验收

比较相同资源下 SQL 拉取、纯推与混合的读取 P99、每帖逻辑索引写入、索引内存、普通作者可见延迟、积压与恢复时间。粉丝规模采用实际可生成并测试的阶梯，不能外推未测成绩。

## 7. 主线二：可靠的派生数据维护

### 7.1 外部处理器接口

保留 SQLHandler 作为 SQL Dummy 的基线测试设施，不把它当作所有处理器的万能接口。

新增投影处理接口，区分：已完成、等待外部任务、可重试、永久失败。网络调用不得被长时间持有的 MySQL 行锁包住。

正常效果的幂等尽可能由目标数据模型实现：固定身份、条件更新、版本检查。SQL 只保留确有业务必要的未决任务/失败审计或批量进度，不为每个成功对象额外新增通用消费行。

### 7.2 事件契约

建议新增并版本化：

- schema_version：消息结构版本。
- event_id：投递与重试身份。
- aggregate_key：帖子或关系等业务对象身份。
- aggregate_version 或 relation_generation：业务变化次序/关系生命周期身份。
- event_type、必要 payload。
- source_position：CDC/日志来源定位信息，不冒充业务版本。

旧消息不得靠 created_on 或全局自增 event_id 猜测对象版本。迁移时显式处理旧格式，必要时回读权威状态并重建当前结果。

### 7.3 失败责任

成功且效果可核实后 ACK；需要继续处理时，先可靠保存后继/重试意图再 ACK。发布重试消息未确认，不能先确认原消息。

有界重试、退避、隔离和失败审计必须保留。数据库日志不是唯一实现方式，但不可恢复的内存队列也不是等价替代。

默认死信转发不能被视为无条件可靠。固定队列类型和版本，验证显式确认转交或适用的 at-least-once dead lettering 配置。[R8]

### 7.4 搜索是第二个投影，不是独立简历主线

使用小批索引、追踪 Meilisearch task UID 和实际成功状态。接口受理不代表索引可见。

不要假定 Meilisearch 与 Redis 具有同样的 CAS 能力。按对象组织处理顺序，处理结果不确定窗口；迟到事件基于当前权威状态处理并进行最终核对。对无法证明顺序的故障情形，使用对账/重建收敛，不能声称只加 version 字段就天然拒绝旧写。

### 7.5 验收

提交后丢响应、确认后未记状态、外部效果后未 ACK、重复/迟到、依赖暂停、失败重放、投影清空重建。核对身份和结果，不只比较总数，不以队列为空证明完成。

## 8. 主线三：热点缓存与一致性恢复

### 8.1 数据分层

L1 进程内只缓存可安全复用的内容/候选；L2 Redis 缓存正文与时间线索引；MySQL 为权威状态。读取命中 L1/L2 不意味着可以跳过删除和关系规则。

同进程同 Key 合并回源；跨实例相同对象通过有限期限的重建资格合并；大量不同 Key 使用总容量约束。Redis 不可用时不能让依赖 Redis 的限流器成为唯一防线。

### 8.2 Lua 的具体用途

- 比较任务/重建 token 与对象代次，再决定是否回填。
- 比较业务版本，拒绝明显迟到的更新；删除标记的保留期与重放窗口配套。
- 对有界时间线进行插入、裁剪与元信息维护。

只做局部短小操作；不在脚本中处理十万粉丝；不在脚本中调用 MySQL。Cluster 多 Key 原子操作需满足同槽约束。[R9-R10]

### 8.3 首轮重建协议：条件提交，不无条件覆盖

1. 原子领取 build token，并读取缓存代次与变更版本。
2. 在 Redis 外读取权威数据，构建有界候选结果。
3. 回填脚本验证 token、代次与变更版本仍匹配。
4. 匹配才提交；不匹配放弃旧结果，按有限重试预算重新构建。
5. 相关实时投影更新必须同步推进目标缓存版本，否则上述比较没有意义。
6. 元信息缺失应拒绝旧构建者，不能把缺失版本当作 0 允许旧回填。

这个协议防止已被观察到的新投影变化被旧构建覆盖，不消除尚未到达缓存的数据库变化。严格业务过滤仍由权威检查保证，后续事件推进投影。高写入下可能反复重建失败，必须限次并保留受控慢路径。

缓存丢失后的重建与消息失败恢复是不同入口：已经 ACK 的事件不会因为缓存清空而自动再来。

### 8.4 验收

旧读晚回、重建期间新帖、删除/取关后旧事件、构建者退出、token 过期、元数据丢失、多个实例同时回源、Redis 整体停机和恢复。记录回源量、有效成功服务、失败类型、拒绝旧回填次数及正确重建结果。

## 9. 主线四：分布式执行与服务治理

这是新增的运行时能力，而不是重复主线二的单事件可靠性。目标是证明横向扩展、故障隔离与集群恢复，而不是拆出固定数量的微服务。

### 9.1 部署角色

- Core API：保留账号、帖子、关注和事务边界；提供少量批量权威状态 RPC。
- Feed 服务：生成和读取时间线候选，独立扩缩容；Fanout/重建可为同模块的独立 worker 进程。
- Indexer：维护搜索投影，隔离搜索依赖与资源。
- Relay/CDC：事件来源适配，作为基础设施角色，不包装成业务微服务。

先拆这几个明确不同的资源域。账户、帖子、关注无需为了数量拆为独立数据库或服务。

### 9.2 RPC 与资源隔离

采用 gRPC；定义批量而非每条帖子一次 RPC 的接口。传播 deadline、取消与 trace ID；区分可安全重试操作；限制重试次数与总时间。客户端 deadline 不等于下游业务已停止，处理器也必须响应取消。[R11]

Feed 读取、分发、重建、搜索分别设并发/连接/队列预算。后续所有指标统计实例总和，不能把每实例限额称作集群限额。

首轮回源保护可按配置的最大副本数 Nmax 预留配额：每实例额度 q 满足 Nmax*q <= 总预算B，超过 Nmax 不允许继续部署同配额实例。这样 Redis 故障时仍有本地保护，但会牺牲低副本时的资源利用率。动态借用配额不进入首轮。

### 9.3 分片工作池

固定逻辑分片数量 P，按目标对象键路由，而不是按当前 worker 数直接取模。调整 worker 数不必重新解释业务路由。

Fanout 在展开后按接收用户归组投递；不能把一个大作者所有工作永久压在一个分片。严格顺序与可并发任务区分；可用多队列 + Single Active Consumer 组织分片内串行与故障接管，跨分片并行。[R12]

RabbitMQ 管理消息消费归属，不再用 etcd 给每条消息加锁。SAC 不使外部写入具有 exactly-once，失联旧消费者仍可能完成已开始的调用，目标版本与幂等协议仍不可少。

增加 worker 并不保证均匀分配或线性提速。需观察每分片负载，实施有界 drain/重新订阅；首轮不实现动态改变 P 与在线重分片。

### 9.4 etcd 的角色

仅用于低频控制面：服务实例目录、带 revision 的资源配置、配置变更通知。实例通过 lease 注册，Watch 更新本地服务目录和配置快照。客户端不在每次业务请求中查询 etcd。

配置完整校验后原子替换；记录生效 revision；断线重连从 revision 恢复，历史被压缩则重新获取快照。etcd 暂不可用时保留已验证配置，拒绝不安全的新变更，不让配置中心抖动立刻拖垮全部数据路径。[R13]

服务目录租约过期不等于旧进程停止，更不构成存储写入 fencing。当前设计不把它当数据唯一写入权。对未来需要独占发布的任务，必须由目标存储验证 epoch/token。

### 9.5 集群实验

- 单 worker 到多 worker：报告固定总资源与增加总资源两种条件，分别解释并行效率与容量变化。
- SIGKILL 一个 worker：检查未完成任务接管、恢复延迟、重复效果与普通业务尾延迟。
- 限制搜索进程/依赖：验证核心发布和 Feed 不被无限等待拖住。
- 修改配置并断开 etcd：观察 revision、重连、旧配置行为。
- 可选 RabbitMQ 三节点 quorum 测试：确认多数派条件与节点故障行为；同一机器上三个容器只代表进程/容器故障实验，不是宿主机或机房容灾。[R8]

MySQL 仍是权威写入入口；应用/worker 能扩展，不等于主库无限可扩展。首轮不宣称整个系统消除了单点。

| P4 | 搜索接入同一投影处理体系 | task UID、实际可见性、删除/旧事件/重建验证 |
| P5 | gRPC 边界、多实例工作池、etcd 控制面 | 扩容、摘除、配置恢复、依赖隔离报告 |
