> 版本：v1.0  
> 日期：2026-11-13  
> 配套需求：[PRD.md](./PRD.md)  
> 定位：说明参照项目、五个 Slot 的工作边界、验收方案和证据口径。

## 1. 首版决定

首版只做五个 Slot：

1. Fanout 与推拉结合。
2. 关注关系建模与查询优化。
3. 近实时搜索索引与同步。
4. 可靠发布与异步事件处理。
5. 热点缓存、受控回源与重建。

账号、纯文本发帖／删帖、最小页面是这些主题的必需产品基础。点赞、计数、评论和其他互动暂不加入；不预留一个必须填满的第六 Slot。

**完成标准是“业务闭环＋可解释的工程取舍＋可复现的证据”，不是功能数量或中间件数量。**

沿用已讨论的技术范围：Go、MySQL、Redis、RabbitMQ、Meilisearch，前端优先裁剪复用 Paopao。是否保留具体框架及如何组织服务，在后续设计中确定，不为学习目的再增加第二种 MQ 或第二种搜索引擎。

产品语义以 PRD 为准。实现可以调整，但不能为了取得更好成绩，改变内容可见范围、删除规则或页面返回条数而不说明。

### 2.3 “组装”不等于将两套工程全部合并

统一保留一套用户身份、一套帖子语义、一套关注关系和一套验收口径。Paopao 提供可使用的产品起点，WeBook 提供学习线索；自己的工作是围绕五个 Slot 建立正确性、恢复能力与测量证据。

上游已有能力不能算作个人新增成果。继承代码的功能也不能绕过相应验收。

## 3. 五个 Slot 的分工

| Slot | 核心问题 | 主要证据 | 不应与之混淆 |
|---|---|---|---|
| S1 Feed | 内容何时预分发、何时读取合并，读写成本如何取舍 | 延迟、写放大、内存、普通任务受影响程度 | MQ 已接入并不等于 Feed 策略有效 |
| S2 关系查询 | 关系如何正确存储与双向查询，深分页如何控制成本 | 查询计划、实际处理量、P99、并发结果 | 关系表不是通用图计算系统 |
| S3 搜索同步 | 搜索如何正确、及时反映帖子变化 | 可搜索时效、索引吞吐、停机追平、删除与重建 | 事件送达不等于索引已可见 |
| S4 可靠事件 | 已提交业务的必要副作用如何跨故障继续 | 故障窗口覆盖、重复效果、遗漏与失败处置 | 不能笼统宣称端到端 exactly-once |
| S5 缓存韧性 | 缓存失效时怎样保护数据库，恢复时怎样重建 | 回源预算、有效服务能力、重建时间与结果 | 队列正常也可能发生缓存丢失 |

S4 与 S5 是可以分别验收的两个维度：昨天已处理并确认的事件，不会仅因今天缓存丢失就自动重新执行；缓存重建也不能弥补从未记录的必需异步工作。它们共享业务规则，但不是同一份成果的不同名称。

## 4. 共用验收约定

### 4.1 三种不同结论

每个 Slot 的报告必须分开给出：

- **正确性通过／失败**：有限测试集中的结果是否满足 PRD。
- **服务目标通过／失败**：是否满足事先冻结的负载、延迟、资源与恢复预算。
- **优化成立／不成立**：相对公平基线是否取得超出运行波动的改善，代价是什么。

功能正确但未跑性能实验，不算性能验收完成；功能和服务目标通过但没有显著提升，也不能写“优化 X%”。

### 4.2 建议数据集

这些是首轮验收建议，不是对生产容量的预判。固定随机种子，记录实际生成数量；资源受限时可以调整，但应在正式对照前冻结。

| 数据集 | 建议规模 | 用途 |
|---|---|---|
| C：可全量核对集 | 200 用户、5000 条有效关注、1 万帖 | 全量计算期望关系和 Feed，验证分页、删除、重放、重建 |
| Q：查询与读取集 | 12 万用户、100 万关注关系、20 万帖 | 双向索引、深分页、100／500／1000 关注者的首页读取 |
| F：分发阶梯集 | 单作者 1000／1 万／10 万独立粉丝，叠加普通作者和读者 | 写放大、内存、积压与混合负载 |
| E：故障事件集 | 1 万条带稳定标识的有效业务事件，另加可识别的无效消息 | 故障恢复、去重、失败处置和结果核对 |

粉丝与关注数量采用有长尾的分布，不要求每个用户同等活跃。不同用户规模、关系规模、请求并发是不同概念。

10 万独立粉丝至少需要 10 万个不同粉丝账号及对应作者；不能用重复关系模拟。只有实际执行百万粉丝实验，才允许在成果中写该规模，不能从十万实验线性推算。

### 4.3 对照条件与测量

1. 固定版本、硬件、CPU／内存额度、实例数、组件版本、持久化设置、连接池、数据种子和请求混合。
2. 页大小固定，Feed 的过滤和排序规则相同；不能关闭删除／关系校验来换性能。
3. 保留基线已有的合理索引和缓存；热缓存对热缓存、冷启动对冷启动，说明所有改动。
4. 正常负载与过载分开测量；高拒绝率不能算作成功吞吐提高。
5. 正式性能场景至少重复 3 轮，建议每轮预热 60 秒、稳定采样 300 秒；实际时长与样本数记录在报告中。小样本不得单独宣称稳定的 P99。
6. 请求到达速率测试优先使用 k6 的 arrival-rate 场景，并检查负载生成器是否实际发出目标请求。服务变慢后客户端也跟着少发请求，可能掩盖排队成本。[T5]
7. 原始请求样本、可见性观察、任务记录和资源曲线均保留，不只保留一张汇总截图。

### 4.4 时间指标的定义

| 指标 | 定义 |
|---|---|
| 发布 API 延迟 | 同一客户端发出请求至收到响应的时间 |
| Feed 首次可见延迟 | 同一观察端从首次发布请求发出，到持续探测中首次从目标用户 Feed 读到帖子的时间；含接入与排队成本 |
| 搜索首次可见延迟 | 从首次发布请求发出，到实际搜索首次返回帖子的时间 |
| 索引任务耗时 | 搜索引擎内部任务的执行／等待时间，单独统计，不替代端到端可见延迟 |
| 恢复追平时间 | 从故障解除到预先界定的故障事件集全部完成，或积压回到冻结的稳态范围 |
| 缓存重建时间 | 从开始恢复指定缓存集合，到该集合通过正确性核对并恢复规定服务能力 |

可见性必须在发压期间持续观察，不能等发压结束才第一次查询。记录轮询间隔、观察者负载和抽样范围；未完成、超时样本单列，不能仅对成功样本取分位数而隐藏失败。

### 4.5 优化前冻结的验收配置

在基线摸底后填写以下参数；填完之后再运行正式优化对照。

| 参数 | 含义 |
|---|---|
| `load_profile` | 数据集、读写比例、请求到达速率、页大小和作者分布 |
| `latency_budget` | 各类成功读取／写入请求的 P95、P99 预算与成功率目标 |
| `visibility_budget` | 普通作者 Feed、搜索和新关注历史补入的时效预算 |
| `fanout_budget` | 分发并发、批量与资源上限；普通任务的可见延迟预算 |
| `fallback_budget` | 回源任务并发、准入速率、最大排队长度和超限响应期限 |
| `minimum_service` | Redis 故障期间最低成功读取速率与写入服务目标 |
| `recovery_budget` | 故障任务追平和缓存重建期限 |
| `strategy_profile` | 作者分类阈值／固定名单、Timeline 容量、补入条数、批量上限等 |

这些是实验配置，不要求新增用户侧配置界面。绝对数值未填写时，只能报告正确性测试或探索性测量，不能宣称完整性能验收通过。

## 5. S1：Fanout 与推拉结合

**对应需求：** PRD 的 F-01～F-08、G-04～G-06、分页和历史内容约定。

### 5.1 具体做什么

保留统一业务语义下的 SQL 拉取基线，建立纯写扩散和推拉混合两种对照策略。普通作者的帖子预分发为用户时间线索引；大粉丝量作者读取时聚合。合并后保证确定性排序、去重和当前状态过滤。

分发需要分批处理和有界并发，避免一次大任务占用无限资源。新关注补入最近历史，近期缓存之外仍能继续读取。

同一运行／实验内固定作者策略，阈值只在独立实验中调整；不做在线自动迁移。对照策略可仅作为测试路径，不要求提供用户侧切换入口。首版不额外引入“仅向活跃粉丝分发”的第四种策略。

### 5.2 验收矩阵

| 编号 | 场景与对照 | 测量 | 必须满足 |
|---|---|---|---|
| S1-A | C 集停止写入且任务追平，比较三种策略 | 每个测试用户的内容 ID、顺序、分页结果 | 按同一参考查询，无不应展示项、无重复、无静止数据遗漏 |
| S1-B | Q 集，读者关注 100／500／1000 个作者，固定负载 | Feed P95/P99、有效吞吐、数据库请求量、读时合并成本 | 达到冻结读取目标；同时报告纯推与混合的读成本差异 |
| S1-C | F 集的大作者分别发帖，比较纯推和混合 | 每帖逻辑索引写入数、Redis 索引内存、总资源与可见延迟 | 成本变化可复现；不能只报减少写入而隐藏读退化 |
| S1-D | 大作者与普通作者同时发布，相同处理资源 | 普通作者可见 P95/P99、积压量和消退时间、goroutine／内存 | 普通任务持续推进，满足冻结时效，资源不越过设计预算 |
| S1-E | 关注补入、取关、重新关注、删帖与迟到事件交错 | 最终 Feed 与权威关系／帖子状态 | 不出现删除复活或迟到清理破坏重新关注结果 |

### 5.3 特别的测量限制

“少写了多少个 Timeline Member”和“进程少用了多少 RSS”不能混为一谈。索引内存应单独统计，并注明包含哪些 Key；Redis `MEMORY USAGE` 是指定 Key 的分配开销估算，不代表整个进程 RSS。[T4]

Timeline 有容量上限时，要报告裁剪情况。比较混合与纯推，不能通过少返回内容、缩短历史范围取得虚假收益。

在持续写入场景中，以冻结的最终一致性窗口检查；全量结果核对则在指定事件处理完毕后执行。期望集合应独立根据测试夹具和权威数据生成，不直接复用被测 Feed 聚合逻辑，避免同源错误。抽样读者的可见性延迟只代表对应样本。

### 5.4 可交付成果

- 一份三种策略的读写成本对照报告。
- 一份普通作者与大作者混合负载报告。
- 正确性核对脚本及原始结果。
- 基于数据解释的策略阈值，不声称存在通用最优阈值。

**可形成的简历证据：** 在实际测试的粉丝规模下，Timeline 写入或索引内存减少多少；读取增加多少成本；普通任务尾延迟如何变化。没有实测的项不填数字。

## 6. S2：关注关系建模与查询优化

**对应需求：** PRD 的 R-02～R-06。

### 6.1 具体做什么

围绕三个查询建立正确、可解释的关系模型：A 是否关注 B、A 关注了谁、谁关注了 A。支持唯一有效关系、两个方向的索引访问和确定性游标分页。

从继承的可运行查询出发优化；已有合理索引必须保留。重点研究关系数量和分页深度对实际处理量的影响，不提前引入图数据库或分库分表。

### 6.2 验收矩阵

| 编号 | 场景与对照 | 测量 | 必须满足 |
|---|---|---|---|
| S2-A | C 集的关系判断与双向列表 | 结果与预期关系集核对 | 方向正确，固定数据下完整翻页无重复、无遗漏 |
| S2-B | Q 集，关注／粉丝列表分别测浅页与深页 | 实际执行计划、迭代器行数与循环数、查询延迟 | 两个方向都有可解释访问路径，没有因为查反方向意外大范围扫描 |
| S2-C | 每页 50 条，位置约 0／1000／1 万／10 万，比较 OFFSET 与已有游标的下一页 | 数据库执行时间、端到端 P99、实际处理量 | 游标路径不再随已越过行数承担同等线性扫描成本；结论有运行证据 |
| S2-D | 同一用户对多目标及同一对关系重复／并发变更 | 唯一有效关系、最终状态、事务失败后的结果 | 不产生重复关系，不产生只有一侧列表可见的永久不一致 |

游标边界可来自正常前序翻页或固定测试夹具，但必须记录获取方式，不能将它宣传为“任意页码免费跳转”。

使用 `EXPLAIN ANALYZE` 检查真实执行信息；普通 `EXPLAIN` 的估算不能替代运行结果。查询执行剖析与正常接口压测分别采样，避免把分析工具开销当成业务延迟。[T3]

### 6.3 可交付成果

- 查询模式与索引选择的简短说明，不需要扩成数据库教材。
- 浅／深分页对照表、执行计划与原始样本。
- 并发关注／取关的正确性结果。
- 新增索引空间与写入成本的记录。

**可形成的简历证据：** 在明确关系规模、页大小和分页深度下，扫描量及 P99 的变化。若底座已足够高效，只写设计与容量验证，不制造低效基线。

## 7. S3：近实时搜索索引与同步

**对应需求：** PRD 的 S-01～S-08、P-05、G-08。

### 7.1 具体做什么

让搜索正确反映新增与删除，支持独立积压、失败恢复及停写重建。先保证同步正确，再比较逐条索引与有大小／等待时间上限的小批量索引。

Feed 与搜索各自必须获得需要处理的业务变化。搜索故障不能令 Feed 工作被意外当作已完成，或让两个消费者竞争掉本应分别处理的事件。

Meilisearch 的写入请求返回任务信息不等于文档已可搜索；需要跟踪任务状态，并用实际查询验证可见性。[T2]

### 7.2 验收矩阵

| 编号 | 场景与对照 | 测量 | 必须满足 |
|---|---|---|---|
| S3-A | 固定中英文样本的关键词查询 | 预期匹配 ID、作者与正文、无匹配和异常表现 | 基本搜索正确，不以自研相关性指标扩张范围 |
| S3-B | 固定发帖速率，逐条索引与小批量索引对照 | 端到端可搜索 P95/P99、任务成功／失败数、有效索引吞吐 | 达到冻结可见性目标；批量收益与等待代价一并报告 |
| S3-C | 重复创建事件、删帖后注入迟到创建事件 | 用户可见结果及最终索引状态 | 不因重复／旧事件恢复已删除正文；恢复后索引与权威状态一致 |
| S3-D | 搜索服务停止 60 秒，期间继续发布和删除，再恢复 | 发帖／Feed 成功率、积压与追平时间 | 搜索故障不阻塞允许接受的主业务；恢复后指定事件集无静默遗漏 |
| S3-E | 暂停内容写入，清空测试索引并重建 | 有效文档 ID 集合、字段内容、重建耗时 | 与主存储一致，不只核对总条数；明确这是停写重建 |

S3-C 同时包含两个层次：用户读取立即遵守删除过滤；异步搜索索引在恢复与追平后正确清理。只在页面上过滤掉错误索引，不能替代索引最终收敛的检查。

### 7.3 可交付成果

- 索引写入粒度与可见性延迟的对照报告。
- 搜索停机与追平记录。
- 删除／重复／乱序案例及停写重建核对结果。

**可形成的简历证据：** 在固定负载下达到的可搜索时效、批量索引吞吐变化、停机后的追平时间。不将整个搜索引擎本身的性能归为个人优化成果。

## 8. S4：可靠发布与异步事件处理

**对应需求：** PRD 的 P-02～P-06、X-01～X-04、第 5 节。

### 8.1 具体做什么

为发布、删除、关注历史补入等必需跨系统副作用建立可恢复处理路径。原则采用事务 Outbox、发布结果确认、消费确认、安全重试、明确失败处置及必要的结果核对。

所有承诺成功的业务写入都需要可靠保存，但不是所有操作都必须发送消息。判断依据是“是否存在不能静默遗漏的外部副作用”，而不是“该操作是否非幂等”。

| 操作 | 必须保留的保证 |
|---|---|
| 发帖 | 业务与必需待办共同成立；同一发布意图重试不重复建帖 |
| 删帖 | 权威状态保存，搜索等派生结果最终同步，旧事件不能复活内容 |
| 关注／取关 | 关系状态正确，约定的补入与维护可恢复，迟到操作不破坏新关系 |
| 纯账号操作 | 满足自身事务与身份语义；无必要副作用时不额外引入 MQ |
| 可丢的预热／非关键统计 | 明确标为尽力而为，不用于承担必需功能 |

RabbitMQ 的 Publisher Confirm 和 Consumer ACK 覆盖不同边界。确认 Broker 接收不等于下游业务完成；连接中断后的重投需要消费者处理重复情况。[T1]

涉及 MySQL 与 Redis／搜索等不同资源时，不能先永久记为“处理完成”，再执行不可恢复的外部副作用。具体实现后续设计，但必须用故障实验覆盖这个间隙。

### 8.2 验收矩阵

| 编号 | 故障窗口／输入 | 恢复后必须满足 |
|---|---|---|
| S4-A | 主事务提交前失败 | 不出现被错误承诺成功的业务；没有只存在必要待办却缺失业务主体的错误状态 |
| S4-B | 主事务已提交、响应未返回或消息尚未投递时强制退出 | 原请求安全重试可找回结果；待办恢复后继续完成，不重复建帖 |
| S4-C | MQ 已确认接收、Outbox 尚未记录完成时强制退出 | 允许再次投递，但最终业务效果不重复 |
| S4-D | 消费者处理了部分粉丝或部分索引工作、尚未确认时退出 | 恢复后重做或续做，目标工作最终完整，无漏段、无错误重复效果 |
| S4-E | RabbitMQ 停止 60 秒再恢复 | 未超出接受预算的已提交工作仍被保留；短时故障按预定策略自动续处理并追平 |
| S4-F | 重复、迟到、不可路由、格式错误或持续失败任务 | 正常任务继续推进；失败可查询、可处置，不能静默消失或无限快速重试 |
| S4-G | 修复永久失败原因后显式重放 | 重放完成必要效果，保留处置记录；不能将人工重放写成自动恢复 |
| S4-H | 主存储短时不可用及保留数据卷的容器重启 | 未确认提交的请求按不确定结果安全重试；已确认成功的业务可查回，不能伪造写入成功 |

对于搜索等内部异步任务，还要覆盖“外部系统已受理，但本服务未记录对应结果”的窗口。验收不以“消息队列已空”代替业务完成。

### 8.3 次数、核对与边界

建议 E 集包含 1 万条可追踪有效业务事件；S4-B／C／D 的核心执行窗口各重复注入至少 20 轮。可以每轮选取受控子集，不要求每个窗口每轮都重跑全部事件。

每轮都记录：已提交业务、待处理工作、完成效果和显式失败。不要仅以汇总数量相等判定正确，要检查稳定身份及目标结果，防止“一处遗漏、一处重复”互相抵消。

临时故障恢复并追平后，在指定有效测试集内要求静默遗漏为 0、重复业务效果为 0。无效消息进入明确失败流程；进入死信状态不计为业务完成。

故障注入需要能在指定位置触发，不只靠随机关闭容器。正常退出与强制退出都应记录；MySQL／MQ 持久化数据卷保留。这里验证的是指定故障模型中的恢复，不是磁盘损毁或跨机房容灾。

### 8.4 可交付成果

- 故障窗口清单、注入方式和对应执行记录。
- 测试事件与最终业务结果的核对报告。
- 失败任务查看、重放的可执行说明。
- 明确区分 Broker 接收、消费者处理、派生状态可见的状态说明。

**可形成的简历证据：** 在多少有效事件、多少轮指定故障中完成恢复，测试范围内有无静默遗漏与重复副作用。可靠性结果本身足以成立，无需附会性能提升。

## 9. S5：热点缓存、受控回源与重建

**对应需求：** PRD 的 X-05～X-08、F-06～F-07、G-08～G-10。

### 9.1 具体做什么

区分时间线 ID 索引与内容数据的读取需求；对相同热点合并回源，对大量不同 Key 限制总工作量，并提供缺失／异常时的受控慢路径和恢复重建。

区分“已构建但没有内容”和“缓存缺失／未构建”。重建期间继续发生的发布、删除、取关必须正确反映到最终结果。

`singleflight` 只能合并同一 Group 内、同一 Key 的重叠执行；不提供跨实例统一限流，也不能合并不同用户的全部 Timeline 查询。[T6]

### 9.2 验收矩阵

| 编号 | 场景与对照 | 测量 | 必须满足 |
|---|---|---|---|
| S5-A | 同一热点 Key 缺失；在受控回源窗口内注入并发读取 | 同一 Group 内实际回源执行次数、共享等待、延迟与错误 | 在无主动 Forget／另起填充轮次的条件下，重叠执行合并为一次；不同实例分别统计 |
| S5-B | 大量不同用户的缓存同时缺失 | 全部实例合计回源并发、任务准入、队列长度、SQL 负载 | 不突破冻结预算，资源不随请求无界增长；不能只靠同 Key 合并解释成功 |
| S5-C | 固定外部负载下 Redis 停止 60 秒，保留业务写入 | 成功读取速率、受控拒绝、超时、DB 压力、写入成功率 | 同时满足资源保护与最低有效服务目标，全部拒绝不算通过 |
| S5-D | 清理测试 Timeline 缓存，恢复时继续发帖和关系变更 | 重建并发、内存、恢复耗时、最终内容集合 | 新内容不被旧快照覆盖，删帖／取关不被回滚，达到冻结重建目标 |
| S5-E | 热缓存、冷缓存、故障回退和恢复后读取对照 | P95/P99、完整请求成功率、全链路 DB 请求量 | 结果语义一致，披露降级成本，不能将异常空列表算成功 |

S5-A 可用同步屏障让同批请求在第一次回源结束前进入，验证合并边界；真实压力测试另行记录多次填充轮次。不能把“一次重叠窗口只执行一次”说成该 Key 永远只查询一次。

### 9.3 回源预算与测试完整性

回源任务并发与数据库 QPS 是两种指标：一个任务可能执行多条 SQL。应同时测量。

例如冻结“所有实例合计最多 8 个回源任务”时，要验证实例总和；不能每个实例各允许 8 个，却报告全局上限为 8。具体额度由容量摸底确定，此数字仅为示例。

故障实验必须包含正常鉴权、关系判断、删除过滤和正文读取。不允许为通过测试临时绕过鉴权或删除检查。回源统计应区分必要的状态检查与完整内容加载，避免把优化目标错误理解成所有 SQL 都必须变成 0。

恢复测试只删除隔离测试数据或指定命名空间，不操作真实用户数据。重建正确性以权威状态和参考查询为准，不以 Redis Key 数量恢复为准。

### 9.4 可交付成果

- 热点合并和大量不同 Key 缺失的对照报告。
- Redis 故障时成功读取、拒绝、超时和 DB 负载的并列曲线。
- 缓存重建期间并发更新的核对结果。
- 资源预算、恢复时间与适用范围。

**可形成的简历证据：** 热点回源减少多少；Redis 不可用期间如何控制数据库压力并保留有效服务；指定规模在多久内正确恢复。不能只展示变低的延迟而隐藏高拒绝率。
