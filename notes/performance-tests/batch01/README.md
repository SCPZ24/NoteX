## 诊断采样

- **Redis 写入受限。** 在 2,048 档，21:26:13 至 21:26:15 的实例级 OOM 累计计数从 114,173 增至 117,737。两次采样 used_memory 均超过 128 MiB 的 maxmemory，策略为 noeviction。该容量由所有逻辑库共享，本轮开始前 DB0 已有 14,074 个键。本轮在 DB15 使用独立前缀。Redis 限制与依赖缓存的接口大量 503 同窗出现。发压器未采集每个 503 的响应体，无法将每次拒绝逐条归因。[Redis 现场](redis-window.txt)
- **SQL 窗口。** 约覆盖 512 档，采样比首个请求早约 0.48 秒。累计耗时最高的是按关注关系取 Feed 的 posts/users 查询，1,864 次调用共耗时 23.72 秒，平均 12.72 ms，共检查 11,867,290 行。该窗口早于失效窗口。[MySQL digest](sql-window.json)
- **Core CPU 与调度。** 首档 30.12 秒 profile 共采到 10.79 CPU 秒，flat 样本主要在 syscall.rawsyscalln（44.02%）和 runtime.kevent（30.95%）。第二档另取 5 秒 trace，调度等待累计约 750 ms。两个采样窗口都早于第 77 秒，不能据此认定停发由 Core CPU 或调度造成。[CPU 摘要](core-cpu-top.txt) · [调度摘要](core-sched-top.txt) · [CPU 原始样本](core-cpu.pb.gz) · [原始 trace](core-trace.out)
