## 高档错误集中在 Feed

- 首个错误是第 0.201 秒的 Feed HTTP 503。到 2,048 档，Feed 贡献 9,166 / 9,170 个 503。4,096 和 8,192 两个目标档的 503 **全部来自 Feed**，两档 Feed 分别只有 36 和 32 个成功响应。它占计划流量的 40%，其余接口的大量成功响应使整体成功率仍在约 60%。
- 全程 Core 日志中，GetFeedRelations 有 94,660 次 ResourceExhausted。该调用读取关注关系前需要获取本地 SQL 执行许可，等候队列已满或等待超过 100 ms 均可返回 cache.ErrBusy，随后映射为 ResourceExhausted。RPC 次数含内部调用，与 HTTP 失败数分别统计。现有采样能定位到 SQL 准入受限，未区分两种拒绝原因。[Core RPC 错误统计](core-rpc-errors.json)
- Redis 开跑前的资源采样约为 67.8 MiB，压测期间 INFO 记录的 used_memory_peak 约为 133.5 MiB，全程采样未见 OOM 计数，evicted_keys 为 0。容器硬上限为 1,536 MiB。本轮的 Core SQL 准入拒绝与上轮 Redis 写入触及 128 MiB 上限是不同层面的观测。[资源与 Redis 采样](resources.jsonl)
- 停发时六个角色均存活。主 Feed 队列有 14,319 条 ready、1 条 unacked，四个 Feed 分片共 1,395 条 ready、4 条 unacked。likes 队列为 0。队列快照采于停发后，后台角色仍在消费。[队列快照](queues.tsv)
- 首档 SQL 采样中，按关注关系读 Feed 的查询累计耗时最高，1,684 次调用平均 12.32 ms。Core 的 30 秒 CPU profile 采到 11.58 CPU 秒，第二档另取 5 秒 trace。这些采样早于两个高档，应与高档错误日志分开解读。[SQL 窗口](sql-window.json) · [CPU 摘要](core-cpu-top.txt) · [调度摘要](core-sched-top.txt) · [原始 CPU profile](core-cpu.pb.gz) · [原始 trace](core-trace.out)

## 配置、预算与清理

业务代码提交 a65aa74，本地 Compose 已应用 Redis 1 GiB 配置，策略 noeviction、AOF everysec。复用 batch01 的数据源并复制到本轮专属库，1,003 个有效会话、1,000 个读者、3 个发帖作者、3,000 条初始关注、2,875 篇有效帖子。种子 5，八类业务按方案占比混排，客户端上限 1,024 在途、超时 2 秒。Core、Feed Query、Feed Rebuilder、Feed Worker、Relay、Like Worker 各一实例。Feed hybrid、点赞 adaptive、4 分片、1 个 Feed Worker、4 个 Worker SQL 连接和 2 个并发任务。就绪探针均成功，/me 和帖子详情成功，Feed 返回 20 条。
